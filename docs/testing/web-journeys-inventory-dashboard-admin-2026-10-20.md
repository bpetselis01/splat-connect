# Web journey inventory: signed-in routes (dashboard, organisation, admin)

Scout output, read-only, 2026-10-20, HEAD cea425f2 on development. Grep + file reads; nothing was run. Shape follows `packages/mobile/tests/journeys.json` and `docs/testing/mobile-journeys-inventory-2026-10-07.md` section 2. Ids are provisional.

Seats: **P** member, **L** org leader (`caps.ledOrgs.length>0`), **A** admin (`profiles.role='admin'`). Setter: who can put the data into the state the screen shows (n/a, P, L, A, mobile, none).

## Gates (shared by every row below)

- **GD (member)**: `middleware.ts` matcher is every page. `/dashboard`, `/upload`, `/notifications` need a session, else redirect `/login`. Then the contributor-terms gate: `/dashboard*`, `/upload*`, `/organizations*`, `/tutorials/:id/edit*` need a `user_agreements` row `contributor_terms` at `AGREEMENT_VERSIONS.contributor_terms`, else redirect `/onboarding/contributor-terms?next=`. It fails OPEN on a read error (the API is the real enforcement, `tutorials.ts` POST). In page: `requireCapabilities()` redirects `/login` if the profile fetch fails. There is no `app/dashboard/layout.tsx`; the rail comes from the root layout.
- **GL (leader)**: GD plus in-page `getCapabilities()`; `ledOrgs.length===0` gives `notFound()`. The org is `actingOrg(caps)` (cookie `ACTING_ORG_COOKIE`, set by server action `setActingOrg`, ignores an org the person does not lead). The API re-checks with `leadsOrg` and RLS. `/dashboard/org/events/[id]` and `/dashboard/messages/[cid]` use the same in-page check or the API thread check.
- **GA (admin)**: middleware needs a session, then `profiles.role==='admin'` else redirect `/`. The terms gate does NOT apply to `/admin`. There is no in-page admin check and no `admin/layout.tsx`. The API enforces with `admin.use('*')` (`admin.ts:18`).
- **Data paths**: `SC` = server component calling `apiClient` (server fetch to the Hono API with the session token). `SA` = inline `'use server'` action calling `apiClient`. `CL` = client component calling `browserApiClient` (browser fetch to the API with the token). `SB` = browser Supabase client direct. `RSC-filter` = `?stage=`/`?tab=` link re-rendering the server component with the same fetched data.
- **Unread buckets** (`packages/types/src/index.ts:1821`): tutorials, exchanges, challenges, organisations. Web clears a bucket only through `<MarkNotificationsRead bucket>` on `/dashboard/tutorials`, `/dashboard/exchanges`, `/dashboard/challenges`, or per row on `/notifications` (`PATCH /api/notifications/:id`). Nothing on web clears `organisations` (see Suspects).

## Suspects

1. **Org-bucket notifications can never be cleared on web.** `org_event_published`, `org_event_changed`, `org_event_cancelled`, `org_story_published`, `org_thanked` all map to bucket `organisations`. No page renders `<MarkNotificationsRead bucket="organisations">`; only `/notifications` per-row PATCH clears them (`app/notifications/page.tsx`). `org_message` sits in the `exchanges` bucket, so a leader's `/dashboard/organisation/messages` thread does not clear it either; only visiting My exchanges does (W-DASH-40, W-DASH-82).
2. **Silent hand-offs on web (no notification, no email that works):** recycling Receive/Decline (W-ORG-27/28); org-request approve/decline (W-ADMIN-23/24: the requester becomes leader with no message and a decline reason is stored with no notice); admin test-print Pass/Fail (W-ADMIN-34); admin add/remove leader (W-ADMIN-19/20); org event delete (W-ORG-17: registrants lose the event without `org_event_cancelled`); leader invite is mail-only and the mailer is off (W-ORG-33). The mobile inventory S10 and S12 list the same gaps; none is fixed.
3. **First handoff confirmation notifies no one** (W-DASH-49): `POST /:id/confirm` only inserts notifications for rival requesters (`toy_rejected`). The counterparty finds out through realtime or a refresh. The same route sends `toy_rejected` for rivals, so the type is overloaded (also used by decline and new-code paths).
4. **Admin idea-report "Remove" has a double path.** W-ADMIN-30 (`PATCH /admin/reports/:id` action remove) and W-ADMIN-31 (`DELETE .../removal`) both end in the exported helper `removeParticipant` (`toy-ideas.ts:225`), which writes `challenge_removed`; the Reinstate path (W-ADMIN-31 is actually DELETE of the removal) sends nothing. Also the `GET /api/ideas/joined` row in my API map showed `notifications` only because that helper sits beside it; it is not a write on read.
5. **Admin account removal has no confirmation step** (W-ADMIN-17): a plain `<form action>` with one danger button deletes the account (and cascades other data), only guarded server-side by the `sole_leader` 409. Compare member self-delete (OTP plus typed DELETE) and the typed-phrase `DeleteEntityButton` used for toys and children.
6. **`PATCH /api/admin/tutorials/:id/status` accepts any status and notifies "rejected" for anything that is not `approved`** (`admin.ts:41,60`). The web only sends `approved` or `rejected`, but a stray `pending` or `draft` body would send `tutorial_rejected`.
7. **Admin queues link into the member thread views** (`/dashboard/exchanges/build/:id`, `/dashboard/print-requests/:id`). They work because `toy_transactions` has an admin RLS policy (026), but the pages render `ToyTransactionThread` with the admin as a third party; accept / decline / confirm buttons depend on `isOwnerSide`/`needsAction` and should not appear. No test seen. Also the `/dashboard` terms gate applies to those links but not to `/admin`, so an admin without contributor terms is bounced to onboarding when following them.
8. **Dead or mobile-only API routes (no web caller):** `POST /api/printers/:id/test-prints` (mobile only, so `/admin/test-prints` has no web feeder), `POST /:id/new-code`, `POST /:id/print-fit`, `POST /:orgId/recycling/:id/cancel`, `POST /api/ideas/:id/constraints`, `GET /api/exchange-costs/mine`, `GET /api/toy-transactions/open-builds` (used by the public makers-wanted page only).
